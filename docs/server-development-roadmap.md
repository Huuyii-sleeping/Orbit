## 2. 用一个例子理解整条链路

以下是贯穿路线的**目标案例**，并非当前已经全部开放的功能：

组织 A 的 Alice 创建一个“生成客户回复”的工作流，Bob 审批后得到结果；组织 B 的 Mallory 即使知道运行 ID，也不能查看、订阅或操作它。服务重启后，A 的运行仍然属于 A，能够继续处理。

| 处理位置 | 必须回答的问题 | 案例中的行为 |
| --- | --- | --- |
| 身份提供方 IdP | 用户是谁，属于哪些组织？ | 登录结果证明 Alice 是 A 的成员 |
| BFF 身份入口 | 登录凭据是否有效，当前选择哪个组织？ | 建立可信的用户与组织上下文 |
| BFF 业务服务 | 此人能否执行此操作？ | 已检查编辑、运行、发布和审批权限，禁止发起人自审批；真实 IdP 联调待验收 |
| 产品数据库 | 数据属于谁，关联是否仍在同一组织？ | 草稿、版本、运行和事件都带组织归属 |
| BFF → Agent | 执行服务如何获得可信身份？ | BFF 从已验证上下文生成服务身份，而非采信浏览器参数 |
| Agent / Runtime | 当前组织能否读写这个运行？ | Mallory 的查询、取消、恢复和 SSE 均被拒绝 |
| 模型 / Memory / 工具 | 执行过程中能访问哪些资源？ | 只能使用 A 获准使用的凭据、记忆和文件；这些领域尚待隔离 |
| 运维与恢复 | 任务失败、重启后怎么办？ | 保持归属，恢复运行，记录失败并支持定位 |

需要区分四个概念：

- **认证 Authentication**：证明“你是谁”。目前复用成熟 OIDC 组件，Orbit 不自己保存用户密码。
- **租户隔离 Tenant Isolation**：保证“你只能进入所属组织的数据范围”。本项目以 `issuer + tenantId` 标识组织，避免不同身份提供方的组织 ID 碰撞。
- **授权 Authorization**：决定“在这个组织里，你能做什么”。属于同一个组织不等于自动拥有发布、取消和审批权限。
- **执行隔离**：约束模型、Memory、文件、网络和工具的访问范围。只给数据库加组织字段不能解决这些问题。

## 3. 当前实现和证据

### 3.1 已实现的基础

| 能力 | 已有实现 | 仍需注意的边界 |
| --- | --- | --- |
| 基础稳定性 | 前期已进行并发、一致性与技能运行相关加固 | 属于持续建设，没有“以后不会故障”的保证 |
| 用户登录 | `express-openid-connect` 处理 OIDC；`jose` 校验签名与声明 | 推荐 Keycloak Organizations；真实 IdP 部署和联调仍需验收 |
| 身份与组织上下文 | 服务端保存已验证的 issuer、组织 ID、用户 ID | 不能由浏览器 body/header 指定可信身份 |
| 组织操作权限（M1-A/M1-B） | 从签名组织角色计算权限，SOP/Workflow service 检查操作权限；记录可信发起人并禁止自审批，控制操作留审计 | 浏览器业务入口仍关闭，真实 IdP 部署待验收 |
| 运行资源边界（M1-C） | 输入、静态展开、节点/流式输出、frame、单 run 事件 journal、产品/原生快照受限；资源失败可查询与回放 | 不能代替进程 CPU/内存隔离或全库容量治理 |
| 组织配额与连接治理（M1-C） | 原子预留每组织 5 个、Agent 总计 50 个未完成运行，waiting 和重启遗留记录计入；分类 HTTP 限流，SSE 每组织 8 条、进程总计 128 条 | 单 BFF、单 Agent，Agent 独占目录；HTTP 内存窗口重启清零，多副本须换共享 Store；默认值尚非生产容量承诺 |
| 草稿与模板写入审计（M1-C） | 创建、保存、删除、导入及派生留可信操作人和固定 mutation；成功审计与业务写入同一 SQLite 事务 | 不记录正文；审计总容量、保留期和归档仍待治理 |
| 产品数据归属 | v7 覆盖 SOP 草稿、版本、模板、AgentVersion；v8 覆盖运行、节点、事件和组织 Profile | 历史本地数据保留在旧命名空间，不自动分配给租户 |
| BFF 运行访问 | 查询、取消、恢复、订阅前检查当前组织的本地运行记录 | 浏览器业务 API 白名单尚未开放 |
| 服务间身份传递 | JSON 与 SSE 请求从可信上下文生成租户 header | header 是编码载体，信任依赖服务 Bearer 凭据和受控传输，本身不是签名 token |
| Runtime 运行归属 | 创建时持久化组织，后续校验归属并保持不可变 | BFF 按组织角色授权；内部 Runtime 信任受控服务并检查组织归属，不能向浏览器暴露服务凭据 |
| 重启与审批恢复 | 真实 Agent 子进程测试覆盖重启、审批幂等和终态 SSE 回放 | Runtime 元数据仍要求单进程使用运行目录 |
| 能力关闭策略 | 未隔离入口与执行节点明确拒绝 | 不可直接扩大白名单来绕过缺少的领域隔离 |

租户 Workflow 当前允许：Start、End、Template、Variable、Human Approval、Iteration、Subworkflow。容器内也递归检查。模型、HTTP、工具、代码、表达式等节点尚未开放。

## 5. 下一轮执行清单：M1

**目标：组织 A 可以在权限约束下完成一个纯数据与审批工作流，组织 B 全程无法访问。**

### M1-A：明确组织角色和权限来源

- [x] 角色来自 IdP 签名 ID Token 的 `orbit_org_roles`，以稳定组织 ID 分别映射；不信任客户端自报角色。
- [x] 建立默认拒绝矩阵，覆盖查看、编辑、发布、运行、取消、审批及成员管理策略预留。
- [x] 明确权限失效规则：固定会话最多 300 秒，新登录读取新角色，有效后通道注销撤销匹配会话；不自动停止已执行任务。
- [x] 认证继续复用现有 OIDC；静态矩阵作为业务策略，不新增密码系统或独立策略引擎。

当前角色为 viewer、editor、publisher、operator、approver、admin，允许组织内组合；发布、审批与编辑分别授权。声明配置、完整矩阵及撤权边界见 [组织角色与操作权限](organization-authorization.md)。M1-B 已接入业务操作检查并禁止发起人自审批；真实 IdP 联调在 M1-D 验收。

**验收：** 即使用户伪造角色、组织参数或持有旧会话，也不能突破已定义的授权边界；权限失效时限有记录。

### M1-B：把权限落实到业务操作

- [x] SOP/Workflow service 校验组织操作权限，controller 将授权错误映射为 403。
- [x] 查询、写入、内联草稿运行和子工作流依赖继续限定当前组织，权限不足时在访问上游前拒绝。
- [x] 审批审计保留真实操作人、决定、时间、运行、interrupt ID 与幂等键哈希；可信发起人不可改写，禁止自审批，历史未知发起人拒绝审批。
- [x] 发布需要 publisher/admin，取消需要 operator/admin；子工作流版本须属于当前组织。发布者不采信请求中的 createdBy。
- [x] BFF 执行业务权限，Agent 验证服务身份与运行归属；本轮未增加可由浏览器提交的授权凭据。

v9 控制审计记录 requested/succeeded/failed，无法保存意图时不执行操作；审计不代表外部副作用可回滚，结果未知需要对账。具体语义见 [组织权限文档](organization-authorization.md)。M1-B 的 HTTP 回归使用测试宿主可信身份，完整 OIDC → 业务 → Runtime 链路留在 M1-D。

**验收：** 同组织不同权限用户的结果符合矩阵；跨组织查询、修改、取消、恢复和 SSE 均不可见或被拒绝；直接请求服务也不能伪造浏览器身份。

### M1-C：补齐开放前的输入与资源边界

- [x] 限制 JSON 请求体、定义大小、展开节点/连边数、混合嵌套深度、迭代数量与预计步数，以及运行/审批输入大小。
- [x] 落实节点及流式输出、frame、容器列表、单 run Workflow journal、产品快照和持久化原生 snapshot 的大小限制；超限终态及重启回放有回归。
- [x] 设置组织运行并发与请求频率限制，明确 429、Retry-After 和 SSE 连接上限；waiting 计额、取消释放和重启有回归。
- [x] 对草稿/模板创建和修改、发布、运行、取消、审批保留必要审计，避免记录凭据和完整敏感输入；SQLite 写入与成功审计同事务。
- [x] 只允许已隔离节点及其依赖，递归拒绝藏在 Iteration、Subworkflow 等容器内的未隔离能力。

**验收：** 畸形、超限和高频请求有明确结果，不导致无界执行或拖垮其他组织。

三批实现的限值、检查顺序、失败语义与测试入口见 [Workflow 输入与运行资源边界](workflow-resource-boundaries.md) 和 [组织运行配额、请求限流与连接治理](organization-resource-quotas.md)。运行资源超限会清除产品输出投影并结束订阅，不回滚已发生的外部副作用。M1-C 已于 2026-11-27 通过当前单 BFF、单 Agent 独占运行目录范围的代码与自动化回归验收；尚不代表生产容量、多副本配额或 M1 整体验收通过。浏览器业务白名单保持关闭。

### M1-D：走通完整入口，再按接口开放

- [ ] 用测试 IdP 走通登录会话 → BFF controller/service → 数据库 → Agent → Runtime。
- [ ] 覆盖组织切换、跨组织 ID、角色不足、审批幂等、SSE 断线回放和重启恢复。
- [ ] 在真实部署的 OIDC 提供方上完成配置联调与验收。
- [ ] 仅将验收通过的具体 API 加入 SaaS 白名单，同步更新部署说明。
- [ ] 完成最小界面/API 联调演示，明确当前开放的节点和限制。

**M1 完成标准：** Alice 编辑并运行，获授权的 Bob 审批，Mallory 全程无法访问；未授权的同组织用户不能审批；服务重启后归属和幂等仍成立。

在 M1 验收之前，不把“数据库已有租户字段”或“已有服务间 smoke”当作开放所有业务 API 的依据。

## 6. 完整后续路线

### M2：模型连接与凭据隔离

**为什么做：** 客户 A 的运行不能使用客户 B 的密钥，模型地址也不能成为访问服务内网的入口。

- [ ] 模型连接按组织归属，分别检查管理连接与使用连接的权限。
- [ ] 配置与密钥分开保存；接口返回脱敏结果，日志与异常不泄露密钥。
- [ ] 根据部署环境采用成熟 Secret Manager/KMS 等方案，验证轮换、失效与恢复。
- [ ] 发布版本引用明确的连接修订，定义删除、恢复和凭据轮换的行为。
- [ ] 对自定义模型地址建立 SSRF 防护，覆盖解析结果、重定向和网络出口。
- [ ] 配置调用超时、取消、并发与消耗限制，记录实际可获取的用量；未知用量不能记成零。

**验收：** 替换连接 ID 不能越权；模型限流、超时、凭据失效可见且释放资源；取消传播到上游；组织消耗上限在并发下有效。

**交付：** 开放不使用工具的 LLM 工作流。模型供应商接入继续复用 Mastra 能力。

### M3：Session 与 Memory 隔离

**为什么做：** 会话列表隔离了，不代表历史、摘要、检索记忆和流式事件都已经隔离。

- [ ] 定义个人私有会话与组织共享会话的产品规则。
- [ ] Session、Message、Run、Memory 使用一致归属，并校验关联。
- [ ] Mastra resource/thread 标识从服务端身份派生，不能采信用户提交的归属参数。
- [ ] 历史、发消息、压缩摘要、取消和 SSE 都检查访问权限；长期记忆检索限定范围。
- [ ] 明确同一会话并发发送的处理规则，区分断开订阅与取消执行。
- [ ] 将摘要、检索索引及相关持久化纳入保留期和删除范围。

**验收：** 跨组织读不到消息、订阅不到事件、检索不到 Memory；刷新和重连不造成重复执行；并发消息顺序与既定策略一致。

**交付：** 开放基础 Agent 聊天、历史与 Memory。

**现有入口：** [chat-service.ts](../apps/agent-cli/src/services/chat-service.ts)、[session-compaction-service.ts](../apps/agent-cli/src/services/session-compaction-service.ts)。这些入口目前存在，不代表已经完成租户隔离。

### M4：技能、文件与工具执行隔离

**为什么做：** 工具会产生真实副作用，可能读取文件、访问网络或执行代码。仅有数据库权限不足以约束执行过程。

- [ ] 区分公共与组织私有技能，隔离元数据、包文件、安装目录和版本引用。
- [ ] 私有包上传、下载、发布与使用分别检查授权，服务管理 token 不作为用户授权替代品。
- [ ] 上传包校验路径穿越、解压体积、文件数量和内容边界。
- [ ] 每次运行使用受控工作目录，只注入获准的凭据与工具。
- [ ] 采用成熟沙箱/容器方案，限制文件、网络、CPU、内存、进程和执行时间。
- [ ] 对外部副作用定义审批、幂等、重试和失败后的人工处理方式。
- [ ] 取消、超时与异常退出后清理本次运行资源，保留必要审计。

**验收：** 恶意技能无法越出既定边界；跨组织文件和凭据不可读；重试不重复产生不允许重复的外部操作；取消后无遗留执行。

**交付：** 按工具类别逐项开放操作能力。代码执行、任意 HTTP 等能力独立验收，不随其他工具一起默认开放。

### M5：长任务、故障恢复与扩容

**为什么做：** 进程内运行与本地持久化不能直接等同于多 Worker 可靠执行。

- [ ] 先确定目标负载、部署副本数，以及允许的任务恢复时间。
- [ ] 明确产品数据库、Runtime 状态和 BFF 投影的权威关系与对账修复方式。
- [ ] 按需求引入成熟队列和共享持久化，禁止多个 Agent 共用当前本地 JSON 运行目录。
- [ ] 建立领取、租约、心跳和失效接管，防止旧 Worker 接管失效后继续产生副作用。
- [ ] 定义排队、执行、等待、取消和终态转换，以及重试次数、退避和人工处置。
- [ ] 支持优雅停机，验证重复消息、并发审批和取消的幂等行为。
- [ ] 如跨主机部署，同步解决登录会话共享、事件回放和连接路由问题。

**验收：** 强制终止 Worker 后任务可以恢复或明确失败；重复领取不重复产生外部副作用；发布后任务不会永久卡住。

**交付：** 有清晰容量和恢复约束的长任务服务。先保持现有模块结构，是否拆服务由实际需求决定。

### M6：可观测性、限额与运维

**为什么做：** 运行可靠不仅需要避免错误，还需要在错误发生后能发现、定位和恢复。

- [ ] 用 requestId、runId 关联 BFF、Agent 和上游调用，日志按需记录租户信息并脱敏。
- [ ] 区分技术日志与业务审计，定义访问权限、保留期和删除规则。
- [ ] 监控错误率、延迟、排队时间、运行成功率、调用用量和资源消耗。
- [ ] 区分存活与就绪检查，配置关键依赖告警、处理手册和责任边界。
- [ ] 建立组织级 API、运行、模型与存储限额，测试并发下的公平性。
- [ ] 制定备份、迁移、回滚和密钥轮换流程，定期做恢复演练。
- [ ] 确定可接受的数据损失 RPO 和恢复时间 RTO，以演练结果验证。

**验收：** 能从一次请求定位到执行失败原因；单租户高负载不会耗尽共享资源；备份可恢复且符合目标。

**交付：** 可运营、可维护的服务。这些任务从 M1 开始随功能持续落地。

### M7：上线验收与小范围试运行

- [ ] 为计划开放的 API 建立权限与跨租户测试矩阵，包含正常、越权和异常路径。
- [ ] 真实 IdP 验证登录、退出、组织切换、成员移除和权限变化。
- [ ] 使用接近实际业务比例的负载，记录容量边界，不能只用单测耗时推断生产性能。
- [ ] 演练上游模型故障、数据库不可用、磁盘满、进程退出和网络中断。
- [ ] 验证数据删除、凭据轮换、备份恢复与发布回滚。
- [ ] 邀请少量组织试用，记录问题、限额与支持方式，再逐步扩大范围。

**验收：** 开放能力有明确权限、容量、恢复与支持边界，关键故障有可执行处理方式。

**交付：** 范围清晰的小规模 SaaS 发布。订阅收费、账单、发票等商业能力另立需求；开始收费前须单独完成支付与账务设计。

## 7. 验证与进度维护

### 每一轮开发的固定顺序

1. 在本页选择一个小目标，例如 M1-A，不同时铺开全部里程碑。
2. 说明用户可观察到的结果、涉及边界和本轮验收条件。
3. 阅读相关实现与测试；行为变化优先以失败回归证明问题，再修复。
4. 完成实现、必要集成验证与本轮测试数据清理。
5. 更新本页清单，记录证据和未解决问题，停在待验收状态。

### 验证层次

| 层次 | 主要证明什么 | 不能替代什么 |
| --- | --- | --- |
| 单元测试 | 权限判断、归属比较、状态转换等具体规则 | 真实装配、网络和持久化行为 |
| 数据库集成 | 事务、迁移、复合键、关联与跨租户查询 | Agent 的文件、凭据和执行边界 |
| 服务间 smoke | BFF 代理与真实 Agent 进程协同 | 浏览器登录与 BFF 完整业务权限 |
| 完整入口集成 | 登录身份到业务结果的一条完整链路 | 生产 IdP 配置、生产容量和故障演练 |
| 部署与故障验收 | 真实配置、重启、恢复、负载及资源边界 | 持续监控和日常运营 |

实现后执行工作区要求的构建、对应 smoke/回归与相关包单元测试；提交前结合影响范围完成全仓检查：

```bash
pnpm build
pnpm test
pnpm check:structure
pnpm check:workflow-boundaries
git diff --check
```

真实 IdP、网络、数据库和外部调用测试应注明环境、是否产生费用及清理范围。无法验证的部分要明确记录，不能标成完成。
